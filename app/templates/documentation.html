1. System Architecture & Component Design

RetentionIQ is structured as a decoupled multi-tier enterprise SaaS solution:

  • Presentation Layer: Responsive HTML5, Bootstrap 5, Chart.js, and client-side table filters styled in a modern Navy & Teal palette.
  • Application Layer: Flask 3.1 with blueprint-based modular routing, structured REST API endpoints, pagination, and transactional database integrity.
  • Domain Services: Pure Python engines for synthetic data generation, temporal feature extraction, explainable churn scoring, offer margin gating, A/B randomization, and outcome tracking.
  • Persistence Layer: SQLAlchemy 2.0 ORM maintaining 100% dialect parity between SQLite (local development) and MySQL (production deployment), enforcing foreign key cascading and check constraints.

3. Business Formulas & Financial ROI Methodology

All experimental metrics are derived from documented causal retention accounting formulas:

  • Treatment Retention Rate ($R_T$): $\frac{\text{Retained Treatment Customers}}{N_{\text{Treatment}}}$
  • Control Retention Rate ($R_C$): $\frac{\text{Retained Control Customers}}{N_{\text{Control}}}$
  • Absolute Incremental Lift: $R_T - R_C$
  • Relative Lift: $\frac{R_T - R_C}{R_C}$
  • Incremental Retained Customers: $(R_T - R_C) \times N_{\text{Treatment}}$
  • Incremental Campaign Benefit: $\text{Incremental Retained} \times \text{Expected Contribution Margin}$
  • Financial Campaign ROI: $\frac{\text{Incremental Benefit} - \text{Incurred Offer Costs}}{\text{Incurred Offer Costs}} \times 100\%$
4. Mandatory Edge Cases Architecture (EC-01 to EC-04)

Detection: FeatureEngineeringService checks sub.canceled_at <= prediction_cutoff. If true, the customer already churned before the observation horizon began.
Handling: Flagged as temporal anomaly, excluded from active feature matrix, and audited in the Data Quality report.

Detection: OfferEligibilityEngine evaluates 10 criteria (status, tenure, MRR, plan, cooldown, contribution margin).
Handling: If any rule fails, dispatch is intercepted, IneligibleCustomerException is raised, and the violated rule codes are logged and presented to the operator.

Detection: UniqueConstraint('experiment_id', 'customer_id') on CampaignContact table and pre-flight check in RandomizedExperimentEngine.
Handling: Raises ExperimentConflictException if a customer is duplicated across groups or assigned simultaneously to conflicting active experiments.

Detection: evaluate_retention_outcomes_with_attribution() detects customers with multiple contacts across campaigns.
Handling: Applies documented Last-Touch Primary Attribution Policy; flags overlapping outcomes as Multi_Attributed_Flagged to retain full contact history while strictly preventing double-counting in incremental ROI.
